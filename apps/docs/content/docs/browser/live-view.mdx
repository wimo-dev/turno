---
title: "Live view and take-over"
description: "Watch what the agent does in an identity's browser, pause it and take the controls."
---

Off by default. Watch what the agent does in an identity's browser, and take the controls when it
needs you (a captcha, a confirmation, a page it does not understand):

```sh
# from the next turno-browser-mcp for the identity
turno-browser set school --live true
# status, and opens the view in your default browser
turno-browser live school
# the agent's next call waits for you
turno-browser pause school
# it goes on, and is told what changed
turno-browser resume school
```

`turno-browser-mcp --identity school --live` turns it on for one server, and `--live-wait 5m`
changes how long a paused call waits (identity.json `"live": { "enabled": true, "wait": "2m" }`;
from `"5s"` to `"30m"`, 2 minutes by default).

The view is a page with the agent's tab as a picture (a screencast over CDP, sent only while a view
is open), a list of tabs with "Follow the agent" (the tab of the latest call) as the default, and
Pause and Resume buttons. While the agent is paused, your clicks, keys and scrolls on the picture go
to that tab. In a headed Chrome you can also use the window itself: `turno-browser pause` brings the
agent's tab to the front.

While you can see the browser, [the agent cursor](/docs/browser/agent-cursor) shows where the agent is on the page. During a pause its frame turns dashed and its badge says so:

![The same page during a pause: a dashed frame and a badge that says paused, you have the controls](/browser-agent-cursor-paused.png)

What a pause does:

- A call that is running finishes. The next call of the agent (every session of the identity)
  waits, up to the live wait; then it fails with a message that says you still have the browser,
  and the next call waits again. A `browser_batch`, `browser_replay` or `browser_act` in progress
  stops at its next step. The natural language and captcha tools (`browser_act`, `browser_extract`,
  `browser_observe`, `browser_solve_captcha`) wait like any other call; tools that do not touch the
  browser (`browser_flows`) are not held.
- While you have the browser, the idle limit does not close it, the tab governor parks and closes
  nothing (a popup you open stays), and a trace (if `record.traces` is on) is saved, so what you do
  is not in it.
- On resume each waiting call starts with a note: how long the pause lasted and what changed (the
  current tab's URL and title, tabs opened and closed, your input in the view). When nothing
  changed the call runs. When something changed, a call that only reads (a snapshot, the tab list,
  `browser_extract`, `browser_observe`) runs; any other call does not, because the refs of the
  agent's last snapshot may point elsewhere, and the agent gets an error that says so, with a fresh
  snapshot.

How it is protected:

- The view is served on 127.0.0.1 only, on a random port. It answers only a browser that holds the
  server's cookie: a random token made at start, never written to disk or logged.
  `turno-browser live` gets a link from the server whose code works once, within two minutes,
  opens it, and never prints it. Requests must name the server by its loopback address (no DNS
  rebinding), and the buttons only work from the view's own page.
- `turno-browser live`, `pause` and `resume` talk to the server through a Unix socket in a private
  folder (mode 700). `~/.local/state/turno/browser/identities/<id>/live.json` says where it is, and
  holds no secret.
- A page that holds a vault value or a password is never shown: before `browser_login` fills a
  form (at once, or key by key with `humanize`), a value goes into a password field, or a replay types a sensitive parameter, the view stops
  sending that page and says it is hidden, until the page navigates. Your input is not sent to a
  hidden page either. With the live view on, the script tools are refused on such a page, as they
  are while recording.
- Your input in the view is not logged, traced or recorded in a flow; a flow being recorded does
  not have what you did, and the resume note says so.

## When the agent asks for you

Some steps only you may do: typing a password, solving a captcha, entering a code from an email
or a text message, a second factor, accepting terms or giving consent. For those the agent calls
`browser_request_human` instead of acting itself. It works with the live view on or off:

```json
{
  "instruction": "Type your password and press Sign in.",
  "target": "e12",
  "until": { "urlChanges": true, "timeoutMs": 300000 },
  "requireHumanClick": false
}
```

- The agent's tab comes to the front (and its window back from the dock), with a banner at the
  bottom of the page that shows the instruction and a Done button, and a ring around `target`
  (a ref from the agent's last snapshot, or a selector, as `browser_click` takes). The banner is
  drawn again on every page you open during the step, and goes away when it ends. The live view
  shows it too.
- Every call of every session waits while you act, as during a pause: calls already running
  finish first, so no input of the agent's reaches the page while the banner is up.
- The step ends on the first of: the URL matches `until.url` (a glob like `**/dashboard*`, a
  regular expression written `/.../`, or text the URL contains) or changes (`until.urlChanges`),
  `until.selector` is visible, you press Done (`until.done: false` hides the button), you resume
  the agent (Resume in the view, or `turno-browser resume`), or the timeout: 5 minutes by
  default, up to 10 (`until.timeoutMs`). That is longer than the live wait, because typing a
  password and solving a captcha, or fetching a code from your email, takes minutes.
- Done counts only a click the browser made from real input (your mouse or keys, or the live
  view's), never one a page script dispatches. With `requireHumanClick` the result says whether
  your own click landed on the target.
- The agent learns why the step ended, the tab's URL and title, the tabs opened and closed, and
  how many times you clicked and how many fields you changed. It never gets what you typed. A
  page where you typed into a password or code field is held like a vault fill: the script tools
  are refused on it until it navigates.
- With a headless Chrome there is no window: the step needs the live view open
  (`turno-browser live <id>`), and the agent is told to ask you for it when it is not. Read mode
  and Camoufox do not have the tool.

### Passkeys

When a page asks for a passkey (to sign in with one or to create one), only you can answer, with
Touch ID, your phone or a security key, in Chrome's own passkey window. turno sees the request
start and hands you the browser by itself, the same way as `browser_request_human`, with a banner
that tells you to use your passkey in that window:

- It starts only for a request that puts Chrome's window up (`mediation` left out, `"optional"` or
  `"required"`). Passkey autofill (`mediation: "conditional"`), which sign-in pages start on load
  and which waits until you pick a passkey in a field's suggestions, never stops the agent.
- The step ends when the request settles, when you press Done, or after 5 minutes. The agent's
  call that clicked "Sign in with a passkey" (or its next call) says how it went: the passkey was
  created or used, you cancelled it or it timed out (pages get the same `NotAllowedError` for
  both), or it failed with the error's name. It never gets the credential or what the page asked
  for.
- Passkeys need a visible Chrome window. The live view shows the page, not Chrome's own windows,
  so with `--headless` and the live view on no step starts, and the agent is told to ask you to
  run the browser with a window (`turno-browser-mcp` without `--headless`). A headless Chrome
  with the live view off does not watch for passkey requests at all. In attach mode only the
  agent's own tabs count; a passkey you use in one of your tabs is yours.
- To see the requests, turno adds a small script to every frame of the agent's pages that wraps
  `navigator.credentials.create` and `get`, only when someone can see the browser (a Chrome
  window, or the live view on), like the agent cursor's `auto`. It reads only whether the call is
  for a passkey and its `mediation`, and how it settled. Read mode and Camoufox do not have it.

With the other settings:

- Attach mode: you already see the agent's tabs in your own Chrome, and a view would stream your
  own tabs, so the view is off and `turno-browser live` says so. Pause and resume work; act in your
  Chrome, then resume.
- Read mode (`"engine": "lightpanda"`): Lightpanda renders no pixels, so there is no view. Pause
  and resume work.
- [Camoufox](/docs/browser/engines#camoufox): the view is a Chrome DevTools Protocol screencast, which Firefox does not
  have, so there is no view. Pause and resume work; with a headed Camoufox, act in its window.
- [A proxy](/docs/browser/network#a-proxy): the view's tab list hides the proxy's user name and password like vault
  values. The proxy signs in inside the browser, so no page holds them to show.
- `"sharing": "tabs"`: a pause holds every session. The view lists every tab with the session that
  holds it and follows the tab of the latest call from any session; pick a tab to stay on it. Each
  held call's note is about its own session's current tab.
- `humanize`: the view shows the humanized pointer moves, but not the sign-in form `browser_login`
  types key by key (the page is hidden first); your own input from the view is sent as is, and is
  never humanized.
- `turno-browser do`: each command is a call of a session like an agent's, so a pause holds it
  too. It prints the pause note as `note:` lines, and a command that the pause kept from running
  fails with exit code 1.
- Natural language actions and captcha solving: held like any call; a `browser_act` run that the
  pause meets stops before its next step and says which steps ran.
- Recordings: see above; screenshots are taken only after the agent's actions, never of yours.
