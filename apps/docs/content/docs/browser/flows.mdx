## Flows: record and replay

An agent can save what it did on a site as a flow and run it again later without working the page out:
`browser_record` with `action: "start"` and a name, the actions, then `action: "stop"`. `browser_flows`
lists the saved flows and `browser_replay` runs one. Flows are files per identity under
`~/.local/share/turno/browser/flows/<id>/`.

Each step keeps the element it acted on four ways (Playwright's own locator, role and accessible
name, visible text, a CSS path), tried in that order on replay; the snapshot ref is kept for
reading only, since refs change with every snapshot. When no locator finds exactly one visible
element, the replay stops and reports the step, each locator and why it did not fit, the steps
that did not run and a fresh snapshot: the agent does that step itself and calls `browser_replay`
again with `from` set to the next step.

### The element must be the same one

A locator that still finds one element is not proof that it is the recorded element: a button
can lose its id to its neighbour, or a field can keep its place under a new label. So each step
also keeps a fingerprint of its element: its role, accessible name, label and nearest landmark,
and the URL of the page with ids in the path as `*`. Before a replayed step runs, the element
its locator found must match it (names compare without case); otherwise the step does not run,
and the replay stops with what differs (`its name is "Delete account", not "Sign in"`) and a fresh
snapshot, so the agent decides from what the page shows now.

With `record.flows` (on by default) the identity also keeps an action cache: the fingerprint of
every element an action worked on, by page and by the selectors that name it, in
`~/.local/share/turno/browser/action-cache/<id>.json` (mode 600, at most 2,000 entries). A later
action that names an element by a selector instead of a ref (a step of `browser_batch`, a
`turno-browser do click '#save'`) is checked against it the same way and refused when the
element is another one. The cache holds what the page shows about an element, never a value typed
into it; a vault value the page shows (the signed-in user's name on a button) is stored as its
mark, and a locator that names an element by one is not kept, in the cache or in a flow.

Measured with `pnpm bench:cache`: a flow recorded by refs (type an email, type a name, click
Save), then replayed 3 times against each of five variants of the page, and its three actions
repeated by CSS selector (`#email`, `#name`, `#save`) on each:

| | Before the check | With the check |
|---|---|---|
| Replay: steps on the recorded element | 42 of 45 | 33 of 39 (85%) |
| Replay: steps on another element | 3 (Cancel took Save's id) | 0 |
| Replay: steps refused | 0 | 6 (15%) |
| Repeated by selector: on the recorded element | 33 of 45 | 30 of 45 (67%) |
| Repeated by selector: on another element | 9 (214 per 1,000 that ran) | 0 |
| Repeated by selector: refused | 0 | 12 (27%) |

The refused steps are the swapped button, the fields whose ids were swapped, and a field whose
label changed from "Email" to "Work email": the right field, refused because its name changed.
A refusal costs the agent one look at the page; a wrong element costs a wrong action.

Text typed into a field becomes a parameter, with what was typed as its default. A sensitive one
keeps no value: a password field, a one-time code or card field, a field named like `password`,
`otp`, `pin` or `token`, a vault value typed by hand, or any parameter the agent lists in
`sensitive` when it stops. A vault sign-in is a `browser_login` step with the site name only.
Replay needs the sensitive values again; a value written `keychain:<item>` is read from the secret
store (`turno-browser secret set <item>`), so the agent never sees it. Into a password or
one-time code field an agent's `browser_replay` types only such a value; a plain one is refused
there, as the agent's own typing is ([password fields](/docs/browser/vault#password-fields-and-credentials)).

```sh
# saved flows and their parameters
turno-browser flows school
# its steps
turno-browser flows school sign-in
turno-browser replay school sign-in --param password=keychain:school-password
```

`turno-browser replay` runs the flow on the identity's Chrome through `turno-browser-mcp`, the
same way an agent's `browser_replay` does; a sensitive parameter is a `keychain:` reference or
is typed at a hidden prompt, never a value on the command line.

## Recordings and traces

On by default, under the disk cap below. Per identity:

```sh
# what to record, from the next Chrome start
turno-browser record school --flows --traces --screenshots
turno-browser record school --off
turno-browser set school --record-traces false --record-max-size 500MB
```

- `flows` saves every session's actions as a flow named `auto-<time>`; the newest 20 are kept. On
  by default.
- `traces` records a Playwright trace (DOM snapshots, network, a screencast) of each browser
  session. Off by default for now: while Playwright traces, Chrome driven through patchright loads
  no image or frame from another site, so a trace would change the pages it records.
  `--record-traces true` turns them on and keeps every one, `false` records none.
- `screenshots` takes a JPEG after each action. On by default, except in attach mode (your own
  tabs) and read mode (nothing is rendered).

Traces and screenshots go to `~/.local/state/turno/browser/identities/<id>/recordings/`, one
folder per browser session, together at most `record.maxSize` (200MB by default; the oldest go
first). `turno-browser traces school` lists them and `turno-browser traces school --open` shows the
last trace in the trace viewer that patchright-core ships, served on 127.0.0.1 in your default
browser. A trace is saved when turno closes the browser (idle limit, `browser_close`, end of the
session) and before a sign-in; if the server is killed, the trace in progress is lost and the
screenshots stay.

A recording never holds a vault sign-in or a password. Before `browser_login` fills a form, or a
value goes into a password field, or a replay types a sensitive parameter, the trace is stopped
and saved; it starts again only after every page that holds the value has navigated away, so
neither the filled form nor the request that sends it is traced, and no screenshot is taken of
that page. Each saved trace is then searched for those values and deleted if it holds one. There
is no video recording, because a video cannot leave a sign-in out. A trace still holds what the
pages showed and their cookies: treat the folder like the profile itself.

The agent's own devtools tools (`browser_start_tracing`, `browser_start_video`) are listed by
default too. While the agent records with them, turno's trace steps aside (both use the same
tracer) and `browser_login` is refused until the agent stops its recording. With
`--record-traces true` the devtools capability is left out, as before.

With the other settings:

- `"sharing": "tabs"`: a flow recording belongs to the agent session that started it, and only
  that session's actions go into it; `browser_replay` runs in that session's own tabs. A trace
  covers the whole browser, so it holds every session's tabs.
- Attach mode: flows work; traces and screenshots are refused, because they could show your own
  tabs. turno says so before it connects, and `turno-browser set` refuses the combination.
- Read mode (`"engine": "lightpanda"`): flows work, but a replayed step that needs Chrome fails
  like any such tool call; traces and screenshots are refused, since Lightpanda renders no page.
- `humanize`: a replay runs each step as the stock tool call, so it moves and types like the
  agent's own calls on that identity.
