## Snapshots

A page snapshot a tool returns inline (`browser_snapshot`, a batch's last snapshot, the snapshot
attached to an error) is compact; after a navigation or an action, Playwright writes the
snapshot to a file and links it. It keeps every element the agent can act on with its ref, and the text a reader needs
(headings, paragraphs, table cells, labels), and leaves out what only adds tokens: wrappers
without a name, the link destination under a named link, separators, text that repeats the name
of the button or link next to it, and refs on elements nobody acts on. Three or more identical
rows without refs become the first one and a count. Refs are Playwright's own, so a ref from a
compact snapshot works in every tool.

A page that is still long once compact (about 15,000 tokens) comes back as a table of contents:
its landmarks and headings with their refs and sizes, and its text fields. `browser_read` with
the ref of a heading or landmark reads that part (a heading's part runs to the next heading of
its level); `browser_read` without a ref reads the whole page, compact, and with `full: true` as
Playwright wrote it, every wrapper, ref and link destination included.
`TURNO_BROWSER_SNAPSHOT=full` in the server's environment turns compaction off.

After an action that stays on the page (a click, a key, a selection, a drag), the result carries
what changed since the last snapshot the agent was given, by ref: the elements changed or added,
each with what is inside it, and the refs removed. Playwright writes the snapshot after an action
to a file and links it; without the changes, an agent that wants to see what its click did calls
`browser_snapshot` and reads the whole page again. The changes come only when they are safe and
smaller: the same session and the same URL as the last whole snapshot, and less than half the
compact page. A navigation, another tab, a long page's table of contents, or a change that is
most of the page leave the result as Playwright writes it, and `browser_snapshot` always returns
the whole page. The changes applied to the last snapshot give the compact page exactly.
`TURNO_BROWSER_SNAPSHOT=compact` turns them off.

Playwright MCP had an incremental snapshot mode and removed it (microsoft/playwright#39777):
it marked the changed nodes inside the whole tree, which saved little. Here the changes replace
the page, and only on the result of an action that had no inline snapshot before.

| Action (`pnpm bench:browser` tasks, then GitHub) | Changes | `browser_snapshot` after it |
|---|---|---|
| Open the "Code" menu on a GitHub repository page | 262 tokens | 7,683 tokens |
| A click on the bench's small fixture pages (6 of 38 actions) | 82 tokens (median) | 109 tokens |
| The other 32 actions: another page or tab, a change over half the page, or no snapshot | none | |

Measured with `pnpm bench:snapshot --public` on 2026-11-25 (tokens are bytes / 4; every page kept
every interactive ref, and the same questions got the same answers from the full snapshot and
from what the agent gets):

| Page | Full | Compact | What the agent gets |
|---|---|---|---|
| Hacker News front page | 12,238 | 3,786 | 3,786 (-69%) |
| GitHub repository page | 18,879 | 7,721 | 7,721 (-59%) |
| Wikipedia search results | 5,842 | 3,040 | 3,040 (-48%) |
| Wikipedia article (Python) | 128,673 | 72,984 | a table of contents of 849 (-99%), then about 2,200 per part read |

## Actions

turno adds `browser_batch` to the browser tools: it runs several actions (`browser_type`,
`browser_click`, `browser_select_option`, ...) in order in one call, stops at the first one that
fails, and returns one line per action plus, when asked, one snapshot at the end. A form filled
in one call costs the agent one round trip instead of one per field.

An action can carry checks in `expect`: `text` the page must show after it, text that must be
`gone`, a part of the `url`, or the `value` its target must hold (the text of a field, the label
of the selected option, `"true"` or `"false"` for a checkbox). The checks wait for the page up to
`timeout` milliseconds (default 5000, at most 30000), so a step that ends with a confirmation
waits for it without a separate `browser_wait_for`. The first action that fails, or whose check
does not hold, stops the batch. Its error starts with a stable code, its line in the batch says the
code, and the result carries a snapshot of the page at the failure, so the agent needs no extra
call to see it:

| Code | What happened |
|---|---|
| `INVALID_ACTION` | nothing ran: an action names no tool of the server or has invalid arguments |
| `ELEMENT_GONE` | the target is not on the page (a stale ref, a selector that matches nothing) |
| `ELEMENT_COVERED`, `ELEMENT_HIDDEN`, `ELEMENT_DISABLED`, `ELEMENT_READONLY`, `ELEMENT_NOT_STABLE` | the target could not be acted on, as for a call of its own |
| `TIMEOUT` | the action or its wait did not finish in time |
| `REFUSED` | the identity's policy, the engine or the guard of password fields refused the action |
| `CHECK_FAILED` | the action ran and its `expect` did not hold; the message says what the page showed |
| `ERROR` | anything else, with upstream's message |

```json
{
  "actions": [
    { "tool": "browser_type", "arguments": { "target": "e5", "text": "Alice" }, "expect": { "value": "Alice" } },
    { "tool": "browser_click", "arguments": { "target": "e9" }, "expect": { "text": "Saved", "url": "/account" } }
  ]
}
```

When a click or a type fails because of the page, the error says why: the element that covers
the target (a cookie banner, a dialog) with its buttons, or that the target is hidden or
disabled, and the next step. The message starts with a code that stays the same from release to
release: `ELEMENT_COVERED`, `ELEMENT_HIDDEN`, `ELEMENT_DISABLED`, `ELEMENT_READONLY`,
`ELEMENT_GONE` or `ELEMENT_NOT_STABLE` (in a JSON result, `code`, and `cover` for the element in
the way). A target in view that another element covers before the call, and still covers it
300 ms later, is named at once: the call does not run, instead of waiting out Playwright's 5
second action timeout.

After an action, turno waits only until the page is done with it: the requests the action
started have finished (or none started within 100 ms), a navigation of the page has reached
`DOMContentLoaded`, and nothing on the page changed for two animation frames. On a page that
reacts at once that takes a few frames, not Playwright's fixed 500 ms. Playwright's own wait is
the most it can take: `settle` (500 ms by default), plus up to 5 s for the requests (10 s after a
navigation) and `settle` again when there were any. `"settle": "100ms"` in `identity.json`
(`turno-browser set school --settle 100ms`) lowers that limit (Playwright's own
`--timeout-settle` wins over it). A change a page makes later on a timer, with no request, may
not be in the result yet: wait for it with `browser_wait_for`. Camoufox and read mode keep
Playwright's wait.

## From the shell

Coding agents that prefer shell commands to MCP tools, and people at a terminal, can drive an
identity's browser with `turno-browser do <id> <action>`. Each command is one tool call to the
identity's `turno-browser-mcp`, the server agents use: the identity's
[background server](#the-background-server), or mcpd [with turno](#with-turno-through-mcpd). So it
acts in the same browser under the same rules: the profile and its sign-ins, the tab locks or the one-session lease, the
engine, humanize, recordings and the vault.

```sh
turno-browser do school open https://mail.example.com/
# the page's tree, with refs like e12
turno-browser do school snapshot
turno-browser do school click e12
turno-browser do school type e5 'quarterly report' --submit
# the visible text
turno-browser do school read
turno-browser do school screenshot --out page.png
# end the session; the browser keeps running
turno-browser do school end
```

`turno-browser do --help` lists every action: `open`, `back`, `snapshot`, `read`, `find`,
`click`, `type`, `press`, `select`, `hover`, `wait`, `screenshot`, `tabs`, `login` (a vault
sign-in), `call` (any tool of the server, such as `browser_batch`), `close`, `session` and `end`.
The command lives under `do` because the other `turno-browser` subcommands take the identity after their own name (`turno-browser show school`), so an identity
named `show` could not be told from the subcommand. `turno-browser school snapshot` works too,
for an identity whose id is not a subcommand; scripts and agents should write `do`.

Output is short and the same every time: `url:` and `title:` lines, then what the action
returned (the snapshot for `snapshot`, the text for `read`, `file:` for a screenshot, `note:` for a
dialog, a new tab or what the tab governor closed). The code Playwright ran and the snapshot file
an action saves on the server are left out; `--snapshot` after an action prints a fresh snapshot.
A failed action prints `error:` and upstream's message on stderr and exits 1. `--json` prints one object (`schemaVersion`, `page`, `result`, `snapshot`, `error`, ...).

### One session per agent or shell

The commands one agent or one terminal shell runs are one session, as an agent's tool calls are,
so they keep their tab between commands. The session stays open between them and its id is
saved in a folder private to your user (`do/` in the background server's folder, or
`~/.local/state/turno/browser-do/` with turno). The session
belongs to the process that runs the commands: a coding agent (Claude Code and Codex start a
short-lived shell for every command; turno looks past it to the agent, or takes the agent a turno
launcher started from `TURNO_SESSION_PID`) or, in a terminal, your shell. It ends when that process
exits, with `end` or `close`, or when the server restarts (the next command then opens a new tab).
`--session <name>` or `TURNO_BROWSER_SESSION` keeps several sessions apart under one owner, for
example two subagents each in its own tab; `session` shows which one a command would use.

| The identity | What a CLI session does |
|---|---|
| `"sharing": "session"` (the default in attach mode) | it holds the identity's lease like an agent session: while it is open (until `end`, or after 5 minutes without a command on the background server, 10 through mcpd), an agent's call is refused with a message that names it, and the other way round |
| `"sharing": "tabs"` (default) | it gets its own tabs next to the agents' and holds them with the same locks; `tabs` marks the others' tabs in use |
| attach mode | one session at a time, as above (attach does not go with tab sharing); it works in turno's own tab of your Chrome, and `close` closes only the tabs turno opened, never your browser. The first command may wait for Chrome's consent dialog (`--timeout`, default 120 seconds) |
| read mode (Lightpanda) | every action works but `screenshot` and `login`: the server refuses those before anything runs, with the reason (Lightpanda lays out no page; read mode keeps no vault sign-ins) |
| humanize | `click`, `type`, `hover`, `select` and `press` move and type like a person, with the latency of the level |
| recordings | each CLI session is one session to the recorder: with `record.flows` its commands become one `auto-<time>` flow; traces and screenshots cover them like an agent's calls |
| vault | `login <site>` fills a vault credential; the value never reaches the shell, its history or the output. Never `type` a password |

### The background server

Without turno, `turno-browser do` reaches the identity through its background server:

```sh
# starts the background server if needed
turno-browser do school open https://example.com
turno-browser do school snapshot
turno-browser do school end
# which background servers run
turno-browser background
# stop one and its Chrome
turno-browser background stop school
```

The background server is `turno-browser-mcp --identity <id> --background`. The first `do` starts
it, detached from the shell (`turno-browser background start <id>` starts it ahead), and it serves
MCP over a Unix socket in `~/.local/state/turno/browser/identities/<id>/background/`, a folder only
your user can enter (on a system without Unix sockets, 127.0.0.1 with a random token per server in
a file only your user can read). Its `server.json` there names its pid, its output goes to
`server.log`, and the sessions of `do` are saved under `do/` there. Each connection is one session
with the identity's sharing rules: one session at a time with `"sharing": "session"` (another
session's call gets an error that names the holder; the hold ends with the session, when its
process exits, or after 5 minutes without a call), its own tabs with `"sharing": "tabs"`. It exits
after 15 minutes without a request, or on `turno-browser background stop <id>`, closing Chrome
first. `turno-browser doctor` lists a running background server under its identity.

While the background server of an identity runs, it alone drives that identity's browser. A
`turno-browser-mcp` that an agent or mcpd started for the same identity answers each call that
needs the browser with an error naming the background server and the command that stops it, and
starts no Chrome; the other way round, the background server does not start while another process
has the identity's Chrome open, and says which one. Calls are never passed from one server to the
other.

To give an agent the identity without turno, `turno-browser setup <agent> --identity <id>` prints
its MCP config (it writes nothing): a `claude mcp add` command for `claude-code`, a
`[mcp_servers]` block for `codex`, an `mcpServers` entry for `cursor`, `copilot` and `gemini`, and
the generic entry for `json`. `--json` prints it as one object for scripts. Secrets that
identity.json names as `keychain:<item>` go in the secret store with `turno-browser secret set
<item>` (the same items `turno secret set` stores). The [turno-browser reference](/docs/reference/turno-browser)
has the help of every command.

### With turno: through mcpd

With turno installed, `turno browser do <id> <action>` runs the same actions through mcpd instead
of a background server, with the same output, session rules (`session`, `end`, `--session`) and
exit codes. The identity must be served by mcpd: its `[server.browser-<id>]` block in `mcp.toml`,
which `turno browser add` prints. When mcpd is not running, the command exits 5. Every other
`turno-browser <command>` on these pages also runs as `turno browser <command>`.

### The skill

The turno plugin for Claude Code adds a short `browser-identity` skill that teaches an agent this
loop (open, snapshot, act by ref, read, end). It tells the agent to read `turno browser do
--help` first, so its instructions always match the installed turno. See
[Skills](/docs/concepts/skills).

## Human-like input

Playwright's own input moves the pointer to the exact center of the target in one move, presses
and releases the button at once, and has `browser_type` insert the whole text without key events.
A site that watches how the page is used can tell that apart from a person. `humanize` in
`identity.json` changes how the same tools move and type, per identity. By default it is `auto`,
which picks the level per page:

- `off` on localhost and for read-only steps (hover, scroll, a pointer move);
- `full` on sign-in, account, payment, checkout and support pages (from the URL), and on a site
  where the identity met a challenge page;
- `light` for every other action.

```sh
# or off, full, adaptive; --humanize "" goes back to auto
turno-browser set school --humanize light
# the server's flag wins over identity.json
turno-browser-mcp --identity school --humanize full
```

| Level | What changes |
|---|---|
| `auto` (default) | `off`, `light` or `full` per page and step, as above. Read mode (Lightpanda) is always `off`. |
| `off` | Playwright's input, except that a click lands at a point inside the target (away from its edges) instead of its exact center, which costs no time. |
| `light` | The pointer travels a curve from where it last was on that page to a point inside the target (one arc, some 4 to 8% longer than the straight line), with small timing jitter; the button stays down for 40 to 90 ms; text up to 80 characters is typed key by key with per-key delays. |
| `full` | `light`, plus a move time that follows the distance and the target's size, a slow-fast-slow speed, overshoot and correction on long moves, a short pause the first time a page is acted on, longer gaps between words, and an element out of view scrolled to in wheel notches. `browser_mouse_wheel` scrolls in notches too. |
| `adaptive` | `light`, and `full` on a site where the identity met a captcha, "verify it's you" or block page (in the [reputation log](/docs/browser/identities#reputation-log) of the last 30 days, or in this session). |

It works through the stock tools (`browser_click`, `browser_hover`, `browser_type`,
`browser_fill_form`, `browser_select_option`, `browser_drag`, `browser_press_key` and the
coordinate tools) and `browser_batch`, without changing their arguments or results. A
`browser_login` sign-in clicks into each field and types its value key by key too; the keys go to
Chrome only, never to a result, a recording or a log. Every event
still goes through Chrome's own input pipeline, and Playwright still checks that the target is
visible, enabled and not covered. Longer text is pasted as before, and a field that is not text
(a date, a color) is filled as before. `"seed"` in the group (`"humanize": { "level": "full",
"seed": 42 }`) makes every path and delay repeat, for debugging; without it each session draws
its own, while the pace (speed, typing rhythm) stays the same for the identity.

It costs time on every action. Measured with Chrome 157 headless on macOS, the median of 8 runs
per tool call:

| Tool call | `off` | `light` | `full` |
|---|---|---|---|
| `browser_click`, 670 px away | 50 ms | 0.5 s | 1.1 s |
| `browser_type`, 11 characters | 10 ms | 2.0 s | 3.5 s |
| `browser_click` on an element 1,500 px below the view | 50 ms | 0.4 s | 2.6 s |

What it does not do: it does not solve captchas (that is a separate opt-in, [Captcha
solving](/docs/browser/natural-language-and-captchas#captcha-solving)), change what the browser reports about itself or hide that a page is
automated from a site that asks. No public study measures how much human-like
input lowers the challenges a site shows, so treat it as a way to act at a human pace on your own
accounts, not as a guarantee. The [acceptable use](/docs/browser/natural-language-and-captchas#acceptable-use) rules apply the same.
